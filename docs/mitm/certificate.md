# 生成与安装证书

HTTPS 解密需要目标客户端信任 B-box 生成的 CA。生成、导出、安装和开启 MITM 是不同操作，需要按顺序完成。

## 1. 生成 CA

进入 **配置 → 编辑 → 高级配置 → MITM → MITM 证书**，点击生成 CA。页面会显示证书身份、SHA-256 和有效期。

根私钥保存在当前设备的 Android Keystore，不能导出。导出的 CRT 和系统 CA 模块只包含公钥证书；生成 CA 本身不会安装信任或启用解密。

## 2. 选择安装方式

| 场景 | 操作 |
| --- | --- |
| Android 7–10，使用用户证书 | 通过证书页面打开 Android 的证书安装入口并完成安装 |
| Android 11 及以后，使用用户证书 | 先导出公钥 CA，再打开安全设置，选择 CA 证书并导入导出的文件 |
| 已使用 Magisk / KernelSU / APatch，需要系统 CA | 导出系统 CA 模块 ZIP，在对应管理器中安装，然后重启 |

厂商设置页面名称可能不同。Android 11+ 的关键顺序是 **导出文件 → 在系统设置中选择该文件**；仅打开设置不代表安装完成。

B-box 不会自动调用 Root 注入证书。系统 CA 模块由 Root 管理器安装，更新或删除后也需要重启。

## 3. 刷新并核对信任

回到证书页，点击刷新信任，核对证书 SHA-256 与刚安装的证书一致，再检查“用户 CA”或“系统 CA”状态。

这个状态描述 B-box 进程所见的证书库。Android 7 起，许多 App 默认不信任用户 CA；目标 App 也可能使用证书固定校验、自有信任库或独立工作资料。因此还需要用实际目标请求验证。

## 4. 开启解密

回到 MITM 页面，填写解密域名，开启 HTTPS 并成功应用配置。重新建立目标连接，再在请求页查看 HTTPS 记录。

若报错，先判断失败在哪一端：

| 现象 | 检查方向 |
| --- | --- |
| 客户端拒绝握手 | 目标客户端是否信任当前 CA，是否存在 pinning 或独立信任库 |
| 上游握手失败 | 真实服务器证书链、名称、有效期、所选出站与连通性 |
| 握手后没有 HTTP 请求 | 查看日志；可能是客户端取消或信任策略，不能直接认定 pinning |

`skip_server_cert_verify` 处理的是 **B-box → 上游** 的校验，不能修复 **目标 App → B-box** 的信任问题。

## 重新生成与换设备

活跃 MITM 或手动记录期间不能重新生成 CA。需要更换时，先停止记录和占用 MITM 的本地服务，再重新生成。

新 CA 与旧 CA 身份不同。需要替换系统/用户/目标客户端中安装的旧证书；系统模块也应更新并重启。清空应用数据、卸载或换设备后，不应继续依赖旧 CA。

配置和备份不携带根私钥或证书安装状态。导入同一 JSON 后，仍要在新设备上重新准备证书。

完整限制见[兼容性说明](../reference/compatibility.md)。
